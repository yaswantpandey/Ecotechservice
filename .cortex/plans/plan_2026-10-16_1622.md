## Codebase review: Ecotech Service (custom PHP MVC, MySQL, FTP deploy to InfinityFree)

**Structure:** `public/index.php` front controller, controllers in `app/controllers` (public, Admin, intern portal), helpers (Security, Mailer, Pdf, OfferLetter), plain PHP views, `.env`-driven `config/config.php`. GitHub Actions deploys over FTP every time you push to `main`.

**Done well:** CSRF uses `random_bytes` and `hash_equals`. Output escaping goes through `Security::e()`. Passwords use bcrypt. The resume upload is solid: it sniffs MIME from file content, picks the extension from a whitelist, uses random filenames and stores files outside the web root. `.env` and resumes are gitignored. In production, errors go to the log, not the page.

### Issues found (most serious first)
1. **Remote code execution through image upload** (`app/helpers/Security.php:105`). `uploadImage()` takes the file extension from the name the client sends. A valid GIF named `x.php` passes the MIME check and gets saved to `public/uploads/...` as a `.php` file, which the server will run. Only admins can upload, but anyone who takes over an admin account (or gets a CSRF/XSS attack through) can take over the server.
2. **No guard on `public/uploads`.** It's gitignored, and I found no `.htaccess` there that stops PHP from running.
3. **Hardcoded fallback secret:** `CSRF_SECRET` defaults to a value that's visible in the repo (`config.php:38`). Placeholder SMTP credentials are also the fallback.
4. **The README publishes the default admin login** (`admin@ecotech.com` / `Admin@123`). Check that it was changed on the live site.
5. **The deploy uploads files the live site doesn't need:** `scratch/*.php` (test scripts, including `mail_test.php`), `global_seo_pages.sql` (only `seo_pages.sql` is excluded), and `.cortex/`. The root `.htaccess` sends all requests into `public/`, so these are probably not reachable from the web. They still shouldn't be on the server.
6. **The deploy doesn't run `composer install`.** `vendor/` is gitignored, so PHPMailer may not be on the server unless you uploaded it by hand.
7. **Minor:** `X-XSS-Protection` is a deprecated header. There's no Content-Security-Policy or HSTS. The session cookie doesn't set `secure` on HTTPS.

I couldn't finish the grep for raw SQL string building (`query("...$var")`) because the tool kept getting interrupted. I'll re-run it before making any changes.

### Proposed fixes
1. `Security::uploadImage`: map MIME to extension (`image/jpeg→jpg`, `image/png→png`, `image/webp→webp`, `image/gif→gif`) and stop using the client's filename. Use `random_bytes` for the name.
2. Add `public/uploads/.htaccess` that turns off PHP and script execution, and un-ignore that one file in `.gitignore` (the same pattern you already use for resumes).
3. `config.php`: in production, fail loudly if `CSRF_SECRET` or the SMTP settings are missing instead of falling back silently. Set `session.cookie_secure` when the request is HTTPS.
4. `ftp-deploy.yml`: exclude `scratch/**`, `*.sql`, `.cortex/**` and `.github/**`. Optionally add a `composer install --no-dev` step before the upload.
5. README: replace the hard-coded admin credentials with a note to set them yourself.
6. Re-run the SQL-injection grep across the controllers and report anything it finds.
